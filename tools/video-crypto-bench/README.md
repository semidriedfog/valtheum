# 영상 암호화 성능 측정

Windows 전용 독립 벤치마크다. 프로젝트 `target/` 아래에 합성 난수 입력을 만들고 일회성 키를 사용한다. 사용자 미디어·DB·설정·`vault.key`는 열거나 변경하지 않는다. 기본 비교 모드의 시제품 형식은 실제 데이터 보호에 사용하지 않는다.

## 적용 코드: 100MB 최종 측정

2026-09-28 이 PC의 D: 드라이브에서 앱에 적용한 **VTV2 / AES-256-GCM / 64KiB** 코드를 100,000,000바이트 입력으로 3회 측정했다. 원본을 한 번 읽으면서 SHA-256과 암호화를 함께 수행하고, 출력 `sync_all` 및 전체 인증 복호화·해시 검증까지 포함한다.

| 항목 | 3회 중앙값 |
|---|---:|
| 전체 시간 | 0.280122초 |
| 해시·암호화·출력 동기화 | 0.185833초 |
| 전체 사본 검증 | 0.097079초 |
| 논리 읽기량 | 200.623216MB |
| 논리 쓰기량 | 100.024666MB |
| 암호화 파일 크기 | 100.024666MB |

MB는 1,000,000바이트다. 단계별 중앙값을 각각 계산하므로 합이 전체 중앙값과 다를 수 있다. 매 회차 시작·25%·50%·75%·끝 위치에서 최대 1MiB씩 복호화하여 원본과 바이트 단위로 비교했다. [최종 적용 코드 원자료](results-20260928-production-100mb.json)에 회차별 시간·I/O·구간 읽기 결과를 보관한다.

## 형식 선정 전 비교 기록

아래 결과는 같은 날짜에 수행한 별도 탐색 실험의 중앙값이다. VTA1은 원본 해시 사전 읽기가 있으며, 통합 시제품은 해시를 인증된 끝부분에 저장한다. **시제품과 최종 VTV2 형식은 다르다.**

| 100MB 방식 | 준비·암호화 | 전체 검증 | 총시간 | 논리 읽기 | 논리 쓰기 |
|---|---:|---:|---:|---:|---:|
| VTA1 64KiB | 0.2368초 | 0.0968초 | 0.3328초 | 300.570MB | 100.025MB |
| 통합 시제품 64KiB | 0.1676초 | 0.1388초 | 0.3090초 | 200.610MB | 100.025MB |
| 통합 시제품 1MiB | 0.1599초 | 0.1567초 | 0.3166초 | 200.587MB | 100.002MB |

각 방식 3회, 순서를 순환했다. [100MB 비교 원자료](results-20260928-100mb.json)를 보존한다. 이전 [1GB 비교 원자료](results-20260928.json)의 총시간 중앙값은 VTA1 3.305초, 통합 시제품 64KiB 2.915초, 1MiB 3.261초였다. 그 실험의 1MiB 구간 읽기 중앙값은 각각 0.883ms·1.176ms·2.646ms다. 64KiB 시제품의 읽기 요청량은 약 1GB 적었지만 모든 구간 읽기에서 VTA1보다 빠른 것은 아니었다. 이 수치를 최종 VTV2의 1GB 실측값으로 해석하지 않는다.

## 재현

프로젝트 루트에서 실행한다. Rust release 빌드와 별도 `Cargo.lock`을 사용하며, 암호화 의존성 `aes-gcm` 0.11.1 등은 앱과 맞춘다.

```powershell
# 적용 코드: 100MB, 3회
cargo run --offline --release --manifest-path tools/video-crypto-bench/Cargo.toml --target-dir target -- 100000000 3 --production

# VTA1과 두 통합 시제품 비교: 100MB, 3회
cargo run --offline --release --manifest-path tools/video-crypto-bench/Cargo.toml --target-dir target -- 100000000 3

# 시제품 왕복·구간·블록 경계·잘못된 키·변조·잘림 검사
cargo test --offline --release --manifest-path tools/video-crypto-bench/Cargo.toml --target-dir target prototype::tests
```

인수는 입력 바이트 수(1~2,000,000,000), 회차(1~5), 선택 사항 `--production` 순서다. 생략하면 1,000,000,000바이트·3회 비교 모드이며 총 9개 출력을 순차 생성한다. 작업 중 원본과 암호화 출력 하나를 유지하고, 시작 전에 입력 크기 3배 + 64MiB의 여유 공간을 확인한다. 빌드 캐시 공간은 별도다. VTA1 비교는 합성 `.zip` 메타데이터 이름을 쓰지만 입력은 실제 ZIP이 아닌 난수 바이트이며 압축 해제·재인코딩을 하지 않는다.

## 측정 범위와 산출물

- `GetProcessIoCounters`의 프로세스 전송량을 측정한다. OS 캐시를 포함한 논리 I/O이며 SSD/NAND 물리 읽기·쓰기나 수명 소모량이 아니다.
- Windows 버퍼 I/O와 생성 직후의 캐시를 사용했고 캐시를 비우지 않았다. 입력 생성·비밀번호 KDF·DB/UI·영상 디코딩은 제외한다. 구간 검증용 원본 읽기도 구간 I/O 측정에서 제외한다.
- 전체 복호화 해시를 입력 생성 시 계산한 독립 해시와 비교한다. VTA1·VTV2의 단계 경계는 진행률 콜백으로 측정하며 총시간·총 I/O는 전체 호출 전후 값이다. 실제 NAS·HDD나 다른 용량에서 같은 속도를 보장하지 않는다.
- 최종 VTV2는 앱의 AES-GCM-HKDF 스트림 안에 해시 footer를 넣은 구현이다. 당시 독립 Python/Tink 복원과 바이트 일치도 별도로 확인했지만, 이 성능 측정이 보안 감사를 대신하지는 않는다.
- 성공한 실행은 자신이 생성한 원본·암호화 파일만 삭제하고 `target/video-crypto-bench-data/<실행ID>/results.json`을 남긴다. 실패하면 해당 합성 데이터를 남길 수 있다. 키는 저장하지 않는다. 소스·`Cargo.lock`·위의 기록된 결과 JSON은 보존하고 재생성 가능한 빌드 캐시만 정리할 수 있다.
